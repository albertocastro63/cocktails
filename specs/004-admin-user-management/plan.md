# Implementation Plan: Admin User Management Interface

**Branch**: `004-admin-user-management` | **Date**: 2026-05-12 | **Spec**: [spec.md](./spec.md)  
**Input**: Feature specification from `specs/004-admin-user-management/spec.md`

## Summary

Add an admin-only interface for managing non-admin user accounts (list, create, edit, delete). Extends the existing backend User model with optional profile fields (first name, last name, email) and a token-version field for immediate session invalidation. Adds four new API endpoints and two frontend pages, with a navigation entry visible only to admin users.

## Technical Context

**Language/Version**: Go 1.21+ (backend), Vanilla JS ES modules (frontend)  
**Primary Dependencies**: `golang-jwt/jwt/v5`, `bcrypt`, `modernc.org/sqlite` (backend); Vite 8, Vitest, Tailwind CSS (frontend)  
**Storage**: SQLite (default), DynamoDB (alternate); both must be updated  
**Testing**: `go test ./...` (backend), `vitest run` (frontend); coverage ≥ 80% business logic  
**Target Platform**: Linux server / local dev  
**Project Type**: Web application (Go backend + Vanilla JS frontend)  
**Performance Goals**: p95 ≤ 200 ms reads, ≤ 500 ms writes (Constitution IV); user list TTI ≤ 3 s  
**Constraints**: No new dependencies; session invalidation via token versioning (DB read per authenticated request); SQLite table rebuild required for FK migration  
**Scale/Scope**: Small user count (< 1000); full list in single response; no pagination in v1

## Complexity Tracking

No constitution violations. The DB read inside `RequireAuthWithStore` on every authenticated request is the only potential performance concern; it is justified because:
- It is a primary-key lookup (O(1), indexed)
- User count is small (< 1000)
- It is the only viable mechanism for immediate JWT invalidation without a blacklist table
- It satisfies the spec's security requirement (FR-014, FR-015)
