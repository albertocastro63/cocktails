# Implementation Plan: Multi-Ingredient Search

**Branch**: `015-multi-ingredient-search` | **Date**: 2026-05-24 | **Spec**: specs/015-multi-ingredient-search/spec.md
**Input**: Feature specification from `specs/015-multi-ingredient-search/spec.md`

## Summary

Extend the existing recipe search (`GET /api/v1/recipes?q=...`) to accept compound ingredient
queries of the form `Gin and Lemon` or `Gin + Lemon + Sugar` and return only recipes whose
ingredient list contains **all** named items. The API contract and frontend UI are otherwise
unchanged; a one-line hint is added below the search bar to surface the syntax.

## Technical Context

**Language/Version**: Go 1.22 (backend), Vanilla JS ES modules (frontend)
**Primary Dependencies**: stdlib `net/http`, `database/sql`, `mattn/go-sqlite3`, AWS SDK v2 for DynamoDB
**Storage**: SQLite (local/dev) with `json_each` queries; DynamoDB (prod) with in-memory filter scan
**Testing**: Go `testing` package + `net/http/httptest`; Vitest for frontend
**Target Platform**: Linux arm64 Lambda (prod), local dev server
**Project Type**: Web service (REST API) + SPA frontend
**Performance Goals**: p95 ≤ 200 ms for `SearchByIngredients` (same as existing `Search`)
**Constraints**: No schema migrations; no new DynamoDB tables; backward-compatible API
**Scale/Scope**: Current recipe count hundreds to low thousands; full-scan acceptable

## Implementation Strategy

### Phase 1 — Store Interface + Tests (TDD)

1. Add `SearchByIngredients(ingredients []string, page, limit int) ([]*model.Recipe, int, error)` to `store.RecipeStore`.
2. Write failing SQLite tests covering: 2-ingredient AND match, 3-ingredient AND match, no-match case, single-empty-token falls through, case-insensitivity, pagination.
3. Write failing DynamoDB tests (using the existing stub pattern).
4. Implement SQLite `SearchByIngredients` using dynamic `json_each` query builder.
5. Implement DynamoDB `SearchByIngredients` using `matchesAllIngredients` filter.

### Phase 2 — Handler + Parser (TDD)

1. Write failing handler tests: `gin and lemon` → two-ingredient result, `gin+lemon` → two-ingredient result, `gin` → single-term (existing path), empty `q` → listing, `gin + + lemon` (empty token) → treated as `gin and lemon`.
2. Implement `parseIngredientQuery(q string) []string` as a standalone function in `handler/` package.
3. Wire handler: if `len(tokens) >= 2` call `SearchByIngredients`, else existing `Search`/`List`.

### Phase 3 — Frontend (TDD)

1. Write failing Vitest tests: hint text is present in RecipeList DOM; existing search tests still pass.
2. Add hint `<p>` element in `RecipeList.js` below the `SearchBar` mount point.

### Dependency Order

```
Store interface (store.go) → SQLite impl → DynamoDB impl → Handler → Frontend
Tests are written per-layer before implementation of that layer.
```
