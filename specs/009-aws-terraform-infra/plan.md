# Implementation Plan: AWS Infrastructure Deployment

**Branch**: `009-aws-terraform-infra` | **Date**: 2026-05-15 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/009-aws-terraform-infra/spec.md`

## Summary

Deploy the full cocktails application to AWS using Terraform with serverless.tf community modules (`terraform-aws-modules`). The deployment provisions a Lambda function (Go, arm64), an HTTP API Gateway, two DynamoDB tables, S3 + CloudFront for the frontend SPA, and CloudWatch log groups with 14-day retention — all in `us-east-1`. A dedicated bootstrap workspace provisions the S3 + DynamoDB state backend once. SAM CLI integration via `null_resource "sam_metadata_*"` blocks enables `sam local start-api` for local testing without deploying.

## Technical Context

**Language/Version**: HCL (Terraform ≥ 1.10), Go 1.25.0 (backend binary, pre-compiled by operator)
**Primary Dependencies**:
- `terraform-aws-modules/lambda/aws ~> 7.0`
- `terraform-aws-modules/apigateway-v2/aws ~> 5.0`
- `terraform-aws-modules/dynamodb-table/aws ~> 4.0`
- `terraform-aws-modules/s3-bucket/aws ~> 4.0`
- `terraform-aws-modules/cloudfront/aws ~> 3.4`
- `hashicorp/aws ~> 5.0`
**Storage**: DynamoDB (application data); S3 (Lambda artifacts, frontend assets, Terraform state)
**Testing**: `terraform validate`, `terraform plan` review, SAM local invocation, `checkov` static analysis
**Target Platform**: AWS `us-east-1`, Lambda `provided.al2023` runtime, arm64 architecture
**Project Type**: Infrastructure as Code (IaC), single-environment deployment
**Performance Goals**: Cold-start API response ≤ 3 s (SC-002); full deploy ≤ 10 min (SC-001)
**Constraints**: Single environment (no multi-env); operator pre-builds binary and frontend assets; credentials configured externally
**Scale/Scope**: Small-scale (< 1k users, < 10k recipes); PAY_PER_REQUEST DynamoDB; no reserved concurrency required

| Principle | Gate Question | Status |

| I. Code Quality | Are HCL modules single-responsibility, below complexity limits, with no duplication? | ✅ |
| II. Test-First | Are failing tests (terraform validate, checkov, SAM local) written before apply? | ⚠ |
| III. UX Consistency | Do all operator-facing commands follow a consistent CLI pattern with clear error output? | ✅ |
| IV. Performance | Does the Lambda cold-start meet ≤ 3 s, and does CloudFront TTI meet ≤ 3 s? | ✅ |
| Quality Gates | Do terraform validate + checkov pass with zero warnings before apply? | ✅ |

**⚠ Principle II justification**: TDD in its strictest form (write failing unit test first) does not directly apply to declarative IaC. The adapted equivalent is:
1. Write `terraform validate` + `checkov` checks that fail on an empty workspace before writing any HCL.
2. Write a SAM local test script (`scenario 5/6` in quickstart.md) that fails before the Lambda is defined.
3. Only then write the Terraform resources.
This satisfies the spirit of test-first development for IaC. Flagged as ⚠ rather than ✅ to be transparent about the adaptation.

```text
infra/
├── bootstrap/                     # One-time state backend setup
│   ├── main.tf                    # S3 state bucket (S3 native file lock, no DynamoDB needed)
│   ├── variables.tf               # project_name, aws_region
│   └── outputs.tf                 # state_bucket_name
├── backend.tf                     # S3 backend config (references bootstrap outputs)
├── versions.tf                    # Provider + module version constraints
├── variables.tf                   # lambda_binary_path, jwt_secret, project_name, environment, aws_region
├── main.tf                        # All application resources (Lambda, APIGW, DDB, S3, CF)
├── outputs.tf                     # api_url, frontend_url, table names
└── samconfig.toml                 # hook_name = "terraform" for SAM CLI
```

**Structure Decision**: Single root Terraform workspace in `infra/` (all application resources). Separate `infra/bootstrap/` subdirectory for one-time state backend provisioning. No sub-modules beyond the registry modules — the single `main.tf` is manageable at this scale and avoids premature abstraction. Frontend asset sync (S3 upload) handled via the `aws_s3_object` resource or Terraform's `fileset()` function within the same workspace.

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Bootstrap workspace (separate from main) | Chicken-and-egg: remote state backend cannot be stored remotely before it exists | Bundling bootstrap into main workspace creates a circular dependency; pure manual CLI commands are undocumented and error-prone (rejected per clarification answer B) |
| SAM metadata `null_resource` (companion resource alongside Lambda) | Required for SAM CLI Terraform hook to discover Lambda functions for local invocation | SAM cannot discover `aws_lambda_function` resources directly without this metadata; the alternative (SAM `template.yaml`) duplicates infrastructure definitions |

## Phase 1: Design Summary

### Key Resource Relationships

```
infra/bootstrap/  ──► S3 state bucket (file lock via use_lockfile = true — no DynamoDB needed)
                        │
                        └──► infra/backend.tf (remote state config)

infra/ (main workspace)
  Artifact S3 ──────────────────────────────────────────────┐
  Lambda Function (cocktails-api) ◄─────────────────────────┘
      │ invoked by
  API Gateway (HTTP, $default route → Lambda proxy)
      │ IAM
  Lambda Execution Role ──────────────────────────────────────►  DynamoDB (recipes + users)
      │ logs
  CloudWatch Log Group (14-day retention)

  Frontend S3 (private) ◄── OAC ── CloudFront Distribution
```

### Infrastructure Tagging

All resources tagged: `project=cocktails`, `environment=<var>`, `managed-by=terraform`.

### Security Posture

- Lambda execution role: least-privilege DynamoDB actions on specific table ARNs only.
- Frontend S3 bucket: completely private; only CloudFront OAC can read objects.
- Artifact S3 bucket: private; only the deploying IAM principal can write.
- API Gateway: no resource policy (open to public); authentication enforced at Lambda (JWT).
- `jwt_secret` variable marked `sensitive = true` in Terraform; never logged.

### Frontend Asset Deployment

Frontend assets (`frontend/dist/`) uploaded to the frontend S3 bucket using `aws_s3_object` resources generated via `for_each` over `fileset("${path.root}/../frontend/dist", "**")`. Content-type set per file extension. CloudFront invalidation triggered after each upload via `null_resource` + `aws_cli` command (or `aws_cloudfront_invalidation` resource if available in provider version).

### SAM Local Environment Variables

SAM local invocations read environment from `infra/env.json` (gitignored). Default values:
```json
{
  "cocktails-api-prod": {
    "STORE_BACKEND": "sqlite",
    "DB_PATH": "/tmp/cocktails_local.db",
    "JWT_SECRET": "local-dev-secret"
  }
}
```
Switch to `"STORE_BACKEND": "dynamodb"` + real table names to test against real DynamoDB locally.
